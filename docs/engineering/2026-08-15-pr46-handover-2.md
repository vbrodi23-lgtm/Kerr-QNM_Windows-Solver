### `a1bb957` — the cross-precision term

`precision_disagreement_abs` had shipped declared and permanently `nothing`, so
the error budget had no term for *is this determinant limited by the width of
the arithmetic carrying it*. That is the one question tightening the controls
cannot answer: at a fixed mantissa, tightening moves control error and
arithmetic error together.

`precision_guard_disagreement` re-evaluates the accepted determinant at the
80-digit rung with every numerical control left exactly as it is, and reports
`|D_full − D_guard|`. Only the stored precision moves; relaxing a control too
would re-measure the control disagreement under a second name and double-count
it in the maximum.

Three invariants make it a like-for-like comparison, and each is enforced in
code rather than assumed:

- **The frozen convention is rounded, not recomputed.**
  `infinity_contour_angle` enters the contour geometry numerically and derives
  from the frequency the *request opened with*, not the one being
  authenticated. Recomputing it would tilt the contour, and the guard would
  report a contour deformation as a precision effect.
- **The branch cell is asserted unchanged.** `GSNBranchCell` holds only
  identity strings and half-plane signs, so a correct rounding leaves it
  identical. If it moves, a reduced mantissa pushed a half-plane sign across
  its boundary and the two evaluations are no longer the same determinant.
- **The guard gets a fresh `ConditioningAccumulator`.** The reported
  conditioning envelope describes the solve whose value is reported, and the
  guard's value never is.

At 80 digits the term is `nothing`, not zero. Absent means *not measured*; zero
would claim *measured and identical*.

Cost: `authenticated_determinant_progress` runs once per `solve_once` at the
accepted root, not per Newton iterate, so this is one extra solve per root.

**Open judgement call, flagged to the user and unanswered.** If the 80-digit
guard throws a control failure, it propagates and fails the leaf rather than
recording the term as absent. Rationale: absent is read downstream as *the
model does not include this term*, which is false when the measurement was
attempted and failed. The risk is turning a leaf red that the 120-digit path
alone would have passed. The 120-digit base tolerances are 1e-24/1e-26,
comfortably inside 80-digit reach, so it is not expected to fire — but if it
does during Gates 1–4, treat it as data, not as a bug to suppress.

Also in this commit: the Python `DeterminantErrorBreakdown` now rejects a
`numerical_error_abs` that does not follow from the components beside it. The
comparison is relative (`1e-40`, at 60 decimal digits of context) because the
worker forms the product in binary and decimal cannot reproduce those bits.

### `d8d55bc` — persistence into caches and reports

`RootReadout.to_mapping`/`from_mapping` is the boundary that `ComponentResult`
and the diagnostic bundles serialise through. Neither side handled
`root_authentication`, so a readout that survived a round trip carried
`converged` with nothing behind it — re-assertable, no longer re-checkable.

`DecimalComplex`, `DeterminantErrorBreakdown` and `RootAuthenticationEvidence`
now emit the same wire form the worker does. `str` on a `Decimal` is exact, so
a 120-digit record is not narrowed to a binary64 shadow on the way to disk.

The leaf report gains `AUTHENTICATION_REPORT_COLUMNS`: the error model, its
four absolute components, the residual and derivative bounds, the selected step
and axis, and the correction bound. They are written as decimal text for the
same reason — these numbers live at 1e-60 and below, where a float rendering
collapses distinct components onto one another.

They are a **sibling** of `CONDITIONING_REPORT_COLUMNS`, not part of it.
Conditioning describes how healthy a solve's arithmetic was; this describes
what the acceptance decision was made on. They are present independently, and
the conditioning tuple is pinned by contract (`test_task3c_conditioning_surfaces`)
and mirrored into the live progress mapping, where acceptance terms do not
belong.

Every column is nullable, never defaulted. A zero in
`precision_disagreement_abs` would claim a measured, perfect agreement where
the exterior Wronskian path simply publishes no error model.

## Task 4 — completed in `c6dae9a`

This one found a real defect rather than confirming an assumption.

Receipt reuse is decided by **exact equality** against
`regularised_gsn_precision_policy(mechanism_id)` in
`_validate_current_promoted_runtime`. The rewrite had added `horizon_contour`
and `determinant_error_model` to that mapping for *both* mechanisms, valued
`None` on the exterior side. A `main`-generated exterior receipt stores the
policy without those keys, so `dict(observed) != expected` — and every exterior
receipt `main` ever produced was rejected as stale, by a change that did not
alter the exterior determinant by a single digit.

Nothing announced it. The policy docstring asserted "exterior receipts are
unaffected"; no test compared the mapping against `main`'s.

Both fields are now carried only under the mechanism they describe, in the
Python policy and in the worker's request flattening and
`validate_regularised_gsn_policy` alike. The worker additionally *rejects* an
exterior request carrying either key, so the two languages cannot drift apart
silently.

The three older mechanism-specific keys
(`scattering_coefficient_extraction`, `horizon_determinant_chart`,
`scattering_chart_safety_factor`) keep their explicit exterior `None`. They are
already part of `main`'s exterior policy, so normalising them now would break
the compatibility this is protecting. The rule going forward: a new
mechanism-specific field is added only under the mechanism it applies to.

Verified diff of the policy mapping against `origin/main`:

```
horizon-admittance  determinant_error_model, homogeneous_representation,
                    horizon_contour, scattering_coefficient_extraction
exterior-fixed-r3   IDENTICAL TO MAIN
```

`tests/test_mechanism_scoped_policy.py` proves both directions. `main`'s
policies are pinned as **literals**, not re-derived from the code under test —
re-deriving would assert only that the function equals itself. The end-to-end
cases drive `_validate_current_promoted_runtime` itself:

- a `main`-generated exterior receipt validates;
- a pre-rewrite horizon receipt raises `_UnauthenticatedComponentEvidence`;
- the current horizon policy is accepted, which anchors the rejection to
  staleness. Without that third case, a horizon path that validated under *no*
  policy would produce the same red-to-green transition and look like proof.

Only the stored policy is stale in these fixtures — the conditioning evidence is
current — so the horizon rejection cannot be coming from some other gate.
Reverting the fix fails eight assertions, including the exterior rejection.
